# フィールド注意事項ポップオーバー プラグイン

kintoneの追加・編集画面で、各フィールドのラベル横に❔アイコンを表示し、クリックするとフィールドごとの注意事項をポップオーバーで表示するプラグインです。

## 構成

```
plugin/
├── manifest.json
├── icon.png
├── html/config.html      # 設定画面
├── js/
│   ├── config.js          # 設定画面ロジック（フィールド一覧取得・保存）
│   └── desktop.js          # アイコン挿入・ポップオーバー表示
└── css/
    ├── config.css
    └── desktop.css
```

### ファイルの役割（`dist/`・`node_modules/`を除く全ファイル）

`plugin/` 配下は実際にkintoneにアップロードされる**プラグイン本体**、プロジェクトルートはそれを**ビルド・配布するための道具一式**という位置づけです。

**プラグイン本体（`plugin/`）**

| ファイル | 役割 |
|---|---|
| `plugin/manifest.json` | プラグインの定義ファイル。名前・説明・アイコン・バージョンや、設定画面(`config`)/実画面(`desktop`)でどのJS・CSSを読み込むかを記述する |
| `plugin/icon.png` | プラグイン一覧に表示されるアイコン画像（現状は仮のプレースホルダー） |
| `plugin/html/config.html` | 設定画面の骨格HTML。「＋ フィールドを追加」ボタンや保存・キャンセルボタンの入れ物で、行の中身はJSで動的生成する |
| `plugin/js/config.js` | 設定画面のロジック。アプリのフィールド一覧をAPI取得し、フィールド選択プルダウン＋注意文入力欄の行を管理、`kintone.plugin.app.setConfig`で保存する |
| `plugin/css/config.css` | 設定画面の見た目 |
| `plugin/js/desktop.js` | アプリの追加・編集画面が開かれたときに動くメインロジック。保存済み注意文を読み込み、フィールドラベルを探して❔アイコンを挿入し、クリック時のポップオーバー表示・URLリンク化を行う |
| `plugin/css/desktop.css` | ❔アイコンとポップオーバーの見た目 |

**ビルド・配布用（プロジェクトルート）**

| ファイル | 役割 |
|---|---|
| `package.json` | npmプロジェクト定義。`npm run pack`で`plugin/`をzip化するスクリプトと、そのために使う`@kintone/plugin-packer`の依存を定義 |
| `package-lock.json` | `npm install`時に依存パッケージのバージョンを固定する自動生成ファイル |
| `private.ppk` | プラグインの署名鍵。**これによってプラグインIDが決まる重要ファイル**。紛失・再生成すると別プラグイン扱いになり既存アプリの設定を引き継げなくなるため、大切に保管すること |
| `.gitignore` | Git管理から除外するファイル指定（`node_modules/`、`dist/`、`private.ppk`）。`private.ppk`は秘密情報として除外している |
| `README.md` | 本ファイル |

## セットアップ

```bash
npm install
```

## パッケージング（zip生成）

初回のみ、署名鍵 `private.ppk` を新規生成しながらビルドします（`--ppk` を付けずに実行すると `dist/` 配下に `<PluginID>.ppk` が自動生成されます）。

```bash
npx kintone-plugin-packer plugin --out dist/plugin.zip
mv dist/*.ppk private.ppk
```

2回目以降は、生成済みの `private.ppk` を指定してビルドします（`npm run pack` で実行可能）。

```bash
npm run pack
```

- `dist/plugin.zip` が生成されます。
- **`private.ppk` によってプラグインIDが決まるため、以降のバージョンアップでも必ず同じ `private.ppk` を使い回してください。** 紛失・再生成すると別プラグイン扱いになり、既存アプリに導入済みの設定（注意事項テキスト）を引き継げません。安全な場所にバックアップしてください。
- `manifest.json` の `version` はアップロードのたびにインクリメントする必要があります。

## kintoneへの導入手順

1. kintoneの「システム管理 > プラグイン > 追加 > zipファイルをアップロード」から `dist/plugin.zip` をアップロード。
2. 対象アプリの「アプリの設定 > プラグイン > プラグインの追加」からこのプラグインを追加。
3. プラグインの設定画面を開き、フィールドごとに注意事項を入力して保存。
4. 「アプリを更新」して本番反映。

## 動作仕様

- 対象画面: 追加画面・編集画面のみ（一覧画面・詳細画面には表示されません）
- 設定画面は「＋ フィールドを追加」で設定行を増やし、行ごとにプルダウンでフィールドを選択して注意事項を入力する方式です。同じフィールドを複数行で重複選択することはできません
- 注意事項が空欄、またはフィールド未選択の行は保存されず、対応するアイコンも表示されません
- サブテーブル配下のフィールドはv1では対象外です
- ❔アイコンはクリックで開閉します。別のアイコンをクリックすると排他的に切り替わり、ポップオーバー外をクリックすると閉じます
- 注意事項テキスト内に `http://` または `https://` で始まるURLを含めると、ポップオーバー内でクリック可能なリンク（新しいタブで開く）として表示されます

## 既知の制限・注意事項

- `kintone.app.record.getFieldElement()` は**仕様上、追加・編集画面では常に`null`を返し**、詳細・印刷画面でのみ有効です。本プラグインは追加・編集画面のみを対象とするため、このAPIには依存せず、画面全体からラベルのテキスト内容がフィールド名と完全一致する要素を探す方式（`findLabelElementByText`）でアイコンを挿入しています。
- ラベルのテキスト一致方式のため、同一フォーム内に**表示ラベルが完全に同じ文字列のフィールドが複数ある場合**、意図しない方にアイコンが付く可能性があります（実運用でラベルが重複するケースは稀です）。
- プラグイン設定の保存容量には上限があります。フィールド数・文言が多い場合は実機で保存できることを確認してください。
- モバイル版kintoneには対応していません（`manifest.json` に `mobile` セクションを追加すれば拡張可能です）。

## 環境依存の懸念点

本プラグインには、kintoneが公式にサポートしていないDOM構造に依存している部分があり、以下のリスクを把握した上で運用してください。

1. **kintoneの将来のUIアップデートで動作しなくなる可能性（最大の懸念）**
   `kintone.app.record.getFieldElement()`が追加・編集画面で使えない仕様のため、`.control-label-text-gaia`などの**非公開のCSSクラス名**を使ってラベル要素を直接探索している（`plugin/js/desktop.js`の`KNOWN_LABEL_SELECTORS`）。サイボウズ側がUIを刷新してクラス名が変わった場合、予告なくアイコンが表示されなくなる可能性がある。複数のクラス名候補でフォールバックしているが、根本的なリスクは解消できない。大きなkintoneアップデート後は簡易動作確認を推奨する。
2. **ラベルテキスト完全一致によるリスク**
   フィールドコンテナではなく「画面に表示されているラベル文字列」で紐付けているため、表示ラベルが重複するフィールドがあると誤って別フィールドにアイコンが付く可能性がある。実機検証の結果、**同名フィールドが複数ある場合は設定画面で先に登録した（＝`fieldNotes`内で先に処理される）フィールドの注意文が、DOM上で最初に見つかったラベル要素（通常はフォームレイアウト上で先に配置されているフィールド）に付き、後から登録した側にはアイコンが付かない**ことを確認済み。同名フィールドに個別の注意文を設定したい場合は、フィールド名を一意にするなど運用面での回避が必要。
3. **他のJavaScriptカスタマイズ・プラグインとの競合**
   同じアプリに、フィールドラベルを動的に書き換える、または同じイベント(`app.record.create.show`/`edit.show`)でDOMを操作する別のカスタマイズが入っている場合、実行順序次第で干渉する可能性がある（読み込み順はプラグイン一覧の並び順に依存）。
4. **設定保存容量の上限**
   `kintone.plugin.app.setConfig`の保存容量は**1プラグインにつき256KBまで**という公式の制限がある（[kintoneヘルプ 制限値一覧](https://cn.kintone.help/k/ja/admin/limitation/limit.html)）。本プラグインは`fieldNotes`というJSON文字列1本に全設定をまとめて保存する方式のため、目安として「1フィールドあたり平均200文字程度の注意文」であれば400フィールド分程度まで保存できる計算になり、通常の運用で容量超過を気にする必要はほぼない。1フィールドに数千文字級の長文を大量に設定するような極端な使い方をする場合のみ、実機で保存できることを確認すること。
5. **モバイル版kintone非対応**
   `manifest.json`は`desktop`セクションのみで、kintoneモバイルアプリでは動作しない。一方、スマートフォンのブラウザでPC版kintoneにアクセスした場合は`desktop`側のJS/CSSが読み込まれてしまう可能性があり、その場合は画面幅が狭いためポップオーバーが画面からはみ出す・❔アイコンが小さくタップしづらいといった**見た目上の崩れ**が起こり得る（レスポンシブ対応はしていない）。
6. **ブラウザ依存は低リスク**
   実装はモダンブラウザのAPI（`NodeList.forEach`等）のみを使用しており、kintoneが公式サポートするブラウザ（Chrome/Edge等）であれば問題ない。

## 実装時の注意点（開発・保守する人向け）

今回の開発で実際にハマった点・設計上の判断を記録している。改修時の参考にすること。

- **`getFieldElement`は追加・編集画面ではnullが返る仕様**（詳細・印刷画面専用）。この制約に気づかず一度実装をやり直した経緯がある。追加・編集画面のフィールドDOMを扱う実装をする際は、まずこの制約を疑うこと。
- **`manifest.json`の`homepage_url`は空文字を許可しない**。使わないなら`homepage_url`キー自体を書かないこと（空文字を入れるとパッケージング時にバリデーションエラーになる）。
- **パッケージングツールの正式パッケージ名は `@kintone/plugin-packer`**（`kintone-plugin-packer`という名前のパッケージは存在しない）。CLIコマンド名自体は`kintone-plugin-packer`。
- **`private.ppk`は`--ppk`オプション指定時、ファイルが存在しないとエラーになり自動生成されない**。初回だけ`--ppk`を付けずに実行して`dist/`配下に自動生成させ、それを`private.ppk`としてルートに配置する必要がある（詳細は「パッケージング」章を参照）。
- **ポップオーバー本文は`innerHTML`を使わずDOM APIのみで構築する**こと。管理者が入力した注意文にURL記法(`[text](url)`)を許すため、任意のHTML注入（XSS）を防ぐ目的で`textContent`/`createElement`/`createTextNode`のみを使う設計にしている。この方針を崩さないこと。
- **プラグイン設定(`kintone.plugin.app.setConfig`)はフラットな文字列キー・バリューしか保存できない**。フィールド数が可変なため、個別キーではなく`fieldNotes`という1つのJSONキーにシリアライズして保存する設計にしている（`plugin/js/config.js`）。
- **ラベル探索はテキスト完全一致**のため、`meta.label`（フィールド定義のラベル文字列）とtrim後で厳密に一致する必要がある。前後の空白や改行が混入すると一致しなくなる点に注意。
